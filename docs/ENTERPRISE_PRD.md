## 1. 结论摘要

### 1.1 主结论：真正的差距不是缺基础设施

通常这类文档会说"上 Postgres、上 Redis、上可观测性"。这些确实都要做，但把它们排在第一位是**错的**。逐文件审计后，差距按修复成本与收益排序是这样的：

```
① 已实现但未接线            ~8 人日     收益最大，风险最低
   产品宣传的能力有相当一部分写完了，但没接进客户实际走的那条路径

② 正确性缺陷（含跨用户数据泄漏）  ~12 人日   必须先修，否则规模化会放大成事故

③ 合规与内容安全            ~45 人日    法律底线，不可延期

④ 平台基础设施              ~95 人日    让服务扛得住并发，是 ⑤⑥ 的前置

⑤ 商业化闭环                ~55 人日
⑥ 拟真度深化                ~55 人日
```

**① 和 ② 加起来 20 人日，却决定了产品"是不是真的能用"。** v1.0 把它们完全漏掉了，直接跳到 ④。

### 1.2 结论一：项目存在系统性的「已实现但未接线」问题

不是个别遗漏，是一类问题。以下能力都已写完、有的还有测试和 API，但**在客户实际使用的 Web 路径上不生效**：

| 能力 | 代码位置 | 实际状态 |
|---|---|---|
| 关系阶段语气（热恋/磨合/分手/治愈） | `core/engine.py:24` `STAGE_INSTRUCTIONS` | **死代码**。有 `GET/PUT /exes/{slug}/stage` 和 `/stage/suggest` 三个 API，存进 meta.json，但**从未注入 system prompt**。用户切换阶段，AI 行为零变化 |
| RAG 查询扩展（18 组情感同义词） | `core/engine.py:44` `KEYWORD_EXPANSIONS` | **死代码**，定义后无任何引用 |
| 记忆衰减 / 遗忘曲线 | `core/memory_decay.py` | **死代码**，与 `core/memory_scorer.py` 互相引用形成闭环，外部零引用 |
| 记忆重要性评分 | `core/memory_scorer.py` | 同上 |
| 隐私脱敏与过期清理 | `core/privacy.py` | **全仓零引用**。敏感信息扫描、脱敏、留存清理三个函数从未被调用过 |
| 镜像导出与数据删除 | `core/exe_lifecycle.py` | **全仓零引用**。v1.0 曾把它当作数据主体权利的现成基础，这是错的 |
| 消息格式化 | `core/message_format.py` | Web 路径未接入 |
| 会话摘要（三层记忆的中间层） | `core/session.py:200` `_generate_summary` | **仅 CLI 生效**。Web 路径永不生成 |
| 人格随对话成长 | `core/session.py:269` `_update_skill_memory` | **仅 CLI 生效**。Web 上镜像永远停在导入那一刻 |
| 流式对话持久化 | `server/routes.py:727` | **缺失**。见结论二 |

**实测验证**：`exes/` 下 6 个镜像，`sessions/` 目录全部为 0 个文件。这意味着 `ChatEngine.session_summaries` 恒为空列表 —— README 宣传的「三层记忆架构」（潜意识层 > 记忆层 > 人格层）在 Web 产品里**实际只跑 1.5 层**：向量库在跑，人格层冻结在导入时刻，记忆层完全空白。

### 1.3 结论二：客户与镜像的所有对话都没有被保存

这是最严重的产品缺陷，且不是设计取舍，是遗漏。

- 前端 `web/static/app.js` 有 5 处调用聊天接口，其中 **4 处走 `/chat/stream`**（第 725、1420、1543、2917 行），只有 1 处走 `/chat`
- `/chat` 会调用 `append_turn` 落库（`server/routes.py:714`）
- **`/chat/stream` 不落库**（`server/routes.py:727-793`，全函数无持久化调用）
- 前端的对话历史来自 `buildHistory(msgsEl)` —— **从 DOM 里读**，然后 `.slice(-50)` 随请求发回服务端

**实测**：6 个镜像里 5 个 `conversation.jsonl` 为 **0 行**（含有真实 9536 字符 SKILL.md 的 `xiaoyu`）。

连锁后果 —— 以下 8 个已上线功能都在读这份空数据：

| 功能 | 代码位置 | 实际表现 |
|---|---|---|
| 对话搜索 | `routes.py:915` | 搜不到任何东西 |
| 统计 | `routes.py:959` | 恒为空 |
| 情感分析 | `routes.py:1012` | 无数据 |
| 阶段建议 | `routes.py:1115` | 无依据 |
| 情感记忆提取 | `routes.py:1232` | 无源数据 |
| 用户画像 | `routes.py:1263` | 无源数据 |
| 关系温度 | `routes.py:1284` | 无源数据 |
| 对话导出 | `core/exporters/conversation.py:49` | 导出空文件 —— 这同时是 PIPL 数据可携带权的实现 |

**对产品定位的直接打击**：客户刷新页面、换设备、清缓存，与"ta"的全部对话即刻消失。镜像也永远不会记得你昨天说过什么。这不是"缺长期记忆功能"，是**核心承诺不成立**。

### 1.4 结论三：存在一个可复现的跨用户数据泄漏

`_engine_cache`（`server/routes.py:119`）以 **slug 为唯一键**缓存 ChatEngine 实例，而 slug 是**全局命名空间**（`config.get_ex_dir` = `EXES_DIR / slug`，不含 user 维度）。

`_invalidate_engine` 只在 3 处被调用：导入（409）、更新（806）、回滚（883）。**删除和创建都不调用。**

复现路径：

1. 用户 A 创建镜像 `xiaoyu`，导入私密聊天记录，对话一次 → A 的 SKILL.md（含其前任的性格画像、私人细节）驻留在 `_engine_cache["xiaoyu"]`
2. A 删除镜像 → `shutil.rmtree(ex_dir)`（`routes.py:369`），**缓存未清**
3. 用户 B 创建镜像，也叫 `xiaoyu` → `create_exe` 仅检查目录是否存在，此时已不存在，创建成功，B 成为 owner
4. B 发起对话 → `_get_engine("xiaoyu")` **命中 A 的旧引擎** → B 在和 A 的前任对话，读的是 A 的人格档案

生产部署是 `restart: unless-stopped` 的长驻单进程，缓存生命周期以周计。`exes/` 现有目录名是 `test`、`test001`、`test123`、`1` —— 正是最容易撞名的那类。

**同一根因还带来第二个问题**：slug 全局唯一意味着 B 创建同名镜像会收到 `409 镜像已存在`，这是一个**存在性预言机**，任何注册用户都能枚举全系统的镜像名。同时用户无法用自己想用的名字。

### 1.5 需要更正 v1.0 的四处结论

审计推翻了 v1.0 的部分判断，列出以便对齐：

| v1.0 的说法 | 实际情况 |
|---|---|
| 数据隔离"有明显短板" | **访问控制实际是合格的**。47 个路由中 29 个带 `{slug}`，**全部 29 个都调用了 `_check_exe_access`**，无一遗漏。问题不在校验覆盖，在缓存键与命名空间设计 |
| 拟真度"缺时间感知" | **时间感知已实现**（`engine.py:_build_system_prompt` 注入当前日期、时刻、星期与分时段话术）。缺的是**相对时间**（距上次对话多久）和纪念日 |
| 把 `RAG_THRESHOLD` 调到 0.5 可提升召回 | **错**。`docs/eval_report.md` 第 2 节实测：阈值 0.5 时召回从 73.1% **降到** 64.6%，但注入条数从 10 降到 4.2、命中率从 12.7% 升到 34.4%。这是**用召回换成本与信噪比**的取舍，不是召回提升 |
| `exe_lifecycle` 是数据主体权利的现成基础 | 它是**死代码**，零引用。实际删除走的是 `routes.py:369` 的裸 `rmtree` |

唯一站得住的量化机会是分块参数：**3 轮/重叠 1 的 Recall@5 为 91.5%，生产配置 `CHUNK_TURNS=5` 只有 71.1%**（`eval_report.md` 第 1 节）。

## 2. 缺陷清单

这是本文档最可直接执行的部分。每条都可复现，带位置、影响与修复量。

### 2.1 严重（上线前必修）

| ID | 缺陷 | 位置 | 影响 | 修复 |
|---|---|---|---|---|
| **D-01** | 引擎缓存不随删除失效，同名镜像重建后返回上一任 owner 的引擎 | `routes.py:119,359` | **跨用户人格档案泄漏** | 删除/创建时调用 `_invalidate_engine`；缓存键改为 `(owner_user_id, slug)`；根治方案是 slug 加用户命名空间 | 
| **D-02** | 流式对话不落库 | `routes.py:727` | 对话全部丢失，8 个下游功能读空数据 | 在 `generate()` 结束处调用 `append_turn`，注意客户端中断时的部分内容处理 |

| ID | 缺陷 | 位置 | 影响 | 修复 |
|---|---|---|---|---|
| **D-06** | `_engine_cache` 无上限、无 TTL、无淘汰 | `routes.py:119` | 每个聊过的 slug 永久驻留一个 ChatEngine（含 ChromaDB 客户端 + 数万字符人格文本）→ OOM | 改 LRU + TTL（同文件的 `SimpleCache` 已有正确实现可复用） |

## 4. 拟真度：从「像 ta 说话」到「觉得就是 ta」

这一节是产品的核心竞争力，也是「让客户真正把这个项目当作自己的前任」这句话的落点。v1.0 在这里写得最空，本版基于对 `core/engine.py`、`prompts/`、`web/static/app.js` 与 `docs/eval_report.md` 的实读重写。

### 4.1 当前的拟真度是怎么产生的

`ChatEngine._build_system_prompt` 每轮拼装：

```
SKILL.md（人格层，实测 2269–5302 tokens）
  ↓
时间感知块（当前日期/时刻/星期 + 分时段话术，80 tokens）
  ↓
最近对话记忆（session 摘要）        ← Web 路径恒为空
  ↓
用户纠正记录（corrections.md）      ← 标注「优先级最高」
  ↓
潜意识层（RAG 检索到的 ta 的原话，top_k=10，score > 0.3 过滤）
  ↓
可用贴纸清单（20 个，157 tokens）
```

设计是对的：**原话优先于描述**。RAG 把 ta 真实说过的话作为语气锚点注入，这比任何"请扮演一个温柔的女生"式的 prompt 都更有效，评测也证实了 —— 有 RAG 时幻觉率 17.9%，无 RAG 基线是 94.5%。

问题在于，这套设计有三层没跑起来（见结论一），以及下面几个更本质的缺口。

### 4.2 让人「相信」的四个维度，当前各缺在哪

拟真不是一个连续标量，是四个可分别攻克的维度。按当前差距排序：

#### 维度一：持续性 —— ta 必须记得

**现状：完全断裂。** 对话不落库（D-02），session 摘要不生成，人格不更新。客户与镜像聊了 100 轮，关掉页面，镜像对这 100 轮**一无所知**。

这不是"缺一个长期记忆功能"，是产品叙事的地基塌了。一个记不住你说过什么的"前任"，客户第二次打开就会失去信任。

修复顺序：D-02 落库 → 把 `session._generate_summary` 与 `_update_skill_memory` 从 CLI 提取为共用服务并接入 Web → 记忆层与人格层才真正开始工作。

#### 维度二：成长性 —— ta 必须变化

**现状：冻结。** 人格停在导入那一刻。CLI 里 `_update_skill_memory` 会把对话摘要追加进 SKILL.md，让镜像随交流演化；Web 没有这条路径。

同时 `corrections.md` 虽然被注入且标了"优先级最高"，但它是**原样全量拼接、永不结构化、永不裁剪**（D-19）。纠正应该沉淀成人格层的结构化条目，而不是无限追加的流水账。

#### 维度三：主动性 —— ta 必须先开口

**现状：完全没有。** 用户不说话，镜像永远沉默。

这是最被低估的一项。真实关系里，"ta 突然发来一条消息"的情绪冲击远大于"我问 ta 答"。一个永远等你先开口的对象，本质上是个工具，不是个人。

需要：时间触发（早晚安）、事件触发（纪念日、生日）、沉默触发（三天没聊）、状态触发（ta"今天心情不好"）。频率必须克制，且**与健康保护联动** —— 处于危机干预状态或已达每日时长上限的用户不推送。

#### 维度四：一致性 —— ta 不能崩人格

**现状：无度量。** 现有 evals 评的是检索准不准、生成有没有编造事实，不评"像不像这个人"。长对话下人格是否漂移、语气是否越来越像通用 AI，完全没有数据。

### 4.3 三个被忽略的"出戏点"

比上面四个维度更具体、修复成本也更低的三处：

**① 回复形态：单气泡 vs 连发短消息**

`web/static/app.js` 已有打字机效果（每字符 30–80ms 随机延迟）与"正在输入"指示器，做得不错。但回复始终渲染成**一个气泡**（`chatBubble('assistant', '')` 后持续追加文本）。

真实微信里，人是**连发多条短消息**的：「在吗」「刚看到」「今天好累」。一整段完整的话反而是最不像微信的说话方式。让模型输出分条、前端分气泡渲染、条与条之间带停顿 —— 这个改动对"像不像"的观感提升，可能大于任何 prompt 调优。

**② 永远秒回**

现在无论深夜还是工作日下午，镜像都以同样速度回复。真人不会。回复延迟应该由 ta 的作息与当前"状态"决定：深夜慢、忙时慢、生气时不回。`app.js:1550` 已有 1–3 秒随机延迟的雏形，需要升级为**由人格与时间共同决定**的延迟模型。

**③ 有求必应**

真人会不想聊、会敷衍、会已读不回、会岔开话题、会打错字。当前镜像永远热情、永远切题、永远流畅。**适度的不完美是可信度的来源**，这需要在人格层显式建模（ta 的回复率、敷衍倾向、错别字模式），而不是靠调高 temperature。

### 4.4 可量化的人格一致性评测

现有 `evals/metrics.py` 已实现 `recall_at_k` / `mrr` / `ndcg_at_k` / `faithfulness_score` 等，架构上完全可以扩展。新增维度：

| 指标 | 定义 | 实现思路 | 目标 |
|---|---|---|---|
| **表达指纹距离** | 生成文本与 ta 真实语料在句长分布、标点习惯、emoji 频率、消息条数分布、口头禅词频上的差异 | 从导入语料统计 ta 的分布，对生成文本算同样分布，取 JS 散度。纯统计，无需 LLM，可进 CI | 建立基线后持续下降 |
| **盲测辨别率** | 人类在「ta 的真实原话 vs 生成回复」二选一中的判别准确率 | 复用 `evals/dataset.py` 的语料，抽样人工标注 | 越接近 50% 越好 |
| **人格漂移** | 长对话（50+ 轮）后表达指纹相对前 10 轮的偏移 | 自动化，可进 CI | 设定漂移上限 |
| **纠正收敛率** | 用户纠正后同类问题的复发率 | 把 corrections 转成评测用例 | 持续下降 |
| **越界率** | 镜像自称 AI、给出百科式回答、使用书面语等出戏行为的比例 | LLM judge，复用 `evals/judge.py` 的论断级判定框架 | 逼近 0 |

**关键**：表达指纹距离和人格漂移都是纯统计指标，不依赖 LLM 判定，成本低、可确定性复现、能直接进 CI 做发布门禁。这是最值得先做的两个。

### 4.5 已验证的检索侧改进空间

`docs/eval_report.md` 的实测结论直接可用：

| 项 | 实测 | 行动 |
|---|---|---|
| 分块策略 | 3 轮/重叠 1 → Recall@5 **91.5%**；生产 `CHUNK_TURNS=5` → **71.1%** | 改配置 + 重建向量。**这是收益最明确的单项** |
| 阈值 | 0.0/0.2/0.3 三者召回完全相同（73.1%），说明 **0.3 形同虚设**；0.5 召回降至 64.6% 但命中率从 12.7% 升到 34.4%、注入条数从 10 降到 4.2 | 这是**成本/信噪比与召回的取舍**，不是免费提升。建议随分块改进后重新扫描 |
| `dominant_speaker=target` 过滤 | 报告第 3 节指出该过滤与窗口大小强耦合，8 轮窗口下候选池枯竭、Recall@5 崩至 21.1% | 改分块参数时必须同步复测该过滤 |
| 查询扩展 | `KEYWORD_EXPANSIONS` 18 组同义词已写好但**从未使用** | 接线并纳入 A/B，是低成本的召回改进候选 |

## 5. 成本与容量模型

v1.0 完全没有这一节。对一个要收费的 SaaS，这是决定生死的部分。

### 5.1 单轮对话的 token 构成（实测）

以 `exes/xiaoyu`（真实镜像，SKILL.md 9536 字符）为例，用项目自己的 `estimate_tokens` 计算：

| 组成 | tokens | 稳定性 |
|---|---:|---|
| SKILL.md 人格层 | 4854 | 稳定 |
| 时间感知块 | 80 | **每分钟变化** |
| session 摘要 | 0 | Web 路径恒为空（接线后会增长） |
| corrections | 0 | 当前为空，会随使用无上限增长 |
| RAG 10 条原话 | ~600 | 每轮变化 |
| 贴纸清单 | 157 | 稳定 |
| **system prompt 合计** | **~5691** | 每轮都要送 |
| 对话历史 | 前端 `.slice(-50)`，上限由 `sanitize_chat_history` 定为 100 轮 × 4000 字符 | 滑动窗口 |

**三个直接结论：**

1. **每轮固定成本约 5700 输入 tokens**，与用户实际输入的长短基本无关。一条"在吗"和一段长倾诉的成本几乎一样。定价必须按**对话轮次**而非字数计。

2. **前缀缓存没有被充分利用**。稳定内容（SKILL.md + 贴纸清单 ≈ 5011 tokens）本可被供应商的上下文缓存覆盖，但每分钟变化的时间块被放在 SKILL.md **之后、其余稳定内容之前**，把可缓存前缀压缩到只剩 SKILL.md。把时间块与 RAG 结果统一移到 system prompt 末尾，即可扩大缓存前缀 —— 当前收益约 15%，且随 corrections 与摘要增长而递增（D-18）。

3. **历史用滑动窗口 `.slice(-50)`**，超过 50 轮后每轮的历史前缀都不同，缓存进一步失效。长对话用户的单位成本会显著高于短对话用户。

### 5.2 容量瓶颈

| 瓶颈 | 当前上限 | 说明 |
|---|---|---|
| 并发 | **1 个进程** | 五处进程内状态 + `fcntl` 文件锁，多副本会直接出错 |
| 事件循环 | **1 个用户导入即阻塞全部** | D-04 |
| 内存 | **无上限增长** | `_engine_cache` 与 `_session_counters` 无淘汰（D-06/D-07）。每个 ChatEngine 常驻数万字符人格文本 + ChromaDB 客户端 |
| 存储 | 单机磁盘 | 每镜像 = 原始记录 + 向量库 + 版本快照，版本快照默认 `include_chroma=True` 会完整复制向量库 |
| 向量库 | 每镜像一个独立 ChromaDB persist 目录 | 文件句柄数随活跃镜像线性增长 |

**结论：当前架构的容量上限不是"几千用户"，是"取决于同时活跃的镜像数与单个导入任务"。** 在 M1 完成前，任何增长都应人工设闸。

### 5.3 计费必须先解决的口径问题

- **流式路径的用量是错的**（D-05）：只估了用户消息与截断历史，漏掉了占大头的 system prompt。按现状计费会严重少收
- **重试放大**：`retry_api` 对永久性错误也重试 3 次（D-09），失败请求同样消耗供应商额度
- **计量不持久**：`_session_counters` 在内存，重启清零（D-07）
- **无成本归集维度**：单一全局 `LLM_API_KEY`，无法按租户拆分供应商账单

在 D-05、D-07、D-09 修复前谈定价没有意义 —— 连自己的成本都算不准。

## 6. 合规与内容安全

这一节是唯一"不做就不能开门营业"的部分。相对 v1.0 结构不变，但补上了审计发现的两处事实修正。

### 6.1 危机干预（最高优先级单项，现状：完全没有）

全仓 grep `自杀|自伤|crisis|suicide|self_harm` **零匹配**。`core/health_tracker.py` 只做使用时长提醒与正念贴士，且状态存在进程内字典。

产品服务失恋、分手、丧失亲密关系（含逝者）场景，用户群本身处于自杀风险高发期。用户表达自伤意念时，系统会继续以"前任"的身份扮演下去 —— 而"前任"的回应恰恰可能是最危险的那类内容。

要求：

- **识别**：关键词表 + 语义模型双通道，宁可误报不可漏报
- **中断角色扮演**：命中后立即退出人格模拟，不再以"ta"的身份回应
- **转介**：以平台身份展示危机干预资源，文案需专业审阅
- **降级而非封禁**：不封号、不删数据，避免用户产生被抛弃感
- **留痕与复核**：事件入审计表，高置信度进人工复核队列
- **强度保护**：`HealthTracker` 的 30 分钟提醒是好起点，需升级为每日时长上限与强制冷静期，且状态迁出进程内存

**边界**：平台不做诊断、不做治疗。干预限于识别、中断、转介三步。

### 6.2 内容安全（现状：完全没有）

| 方向 | 拦截对象 | 处置 |
|---|---|---|
| 用户输入 | 自杀 / 自伤 / 危机意念 | **优先于一切其他处理**，走 6.1 |
| 用户输入 | 涉政、涉黄、违法犯罪、辱骂 | 拒绝并提示 |
| 模型输出 | 违规内容 | 拦截并重新生成或返回兜底话术 |
| 模型输出 | 诱导自伤、鼓励沉溺、承诺复合 | 拦截 |
| 导入语料 | 违规内容 | 标记，不入向量库 |

接第三方内容安全服务为主通道，**本地关键词表兜底**，避免第三方不可用时完全裸奔。

注：`core/validation.py` 已有 7 条 prompt 注入检测模式并在主链路生效，这是好的基础，但它防的是**越狱**，不是**内容违规**，两者不能互相替代。

### 6.3 第三方个人信息的合法性基础

本产品的结构性法律风险，无法完全消除，只能降到可接受并留痕。用户 A 上传 A 与 B 的聊天记录，系统提取 B 的语气、性格并生成模拟 B 的 AI，B 从未同意。

| 层 | 措施 |
|---|---|
| 告知与承诺 | 上传前强制独立确认：声明拥有合法处理基础 |
| 用途限制 | 禁止用于冒充、诈骗、骚扰、对外分发 |
| 技术限制 | 镜像默认私有、不可分享；导出包加密并水印 |
| 最小化 | 原文只用于 RAG 检索，**不用于任何模型训练**，不做跨用户语料聚合 |
| 权利通道 | 为**被模拟者**提供独立投诉与删除通道，无需注册 |
| 逝者处理 | 按 PIPL 第 49 条处理近亲属权利主张。本产品高频场景，必须单列流程 |
| 留存限制 | 原始记录留存期上限（建议 180 天），用户可缩短 |

**审计修正**：v1.0 说 `core/privacy.py` 的脱敏与留存清理"已有基础，未在主链路强制调用"。实际情况更糟 —— **它零引用，从未被调用过**，包括 CLI。`clean_expired_conversations(retention_days=90)` 这个函数写好了，但没有任何定时任务或调用点触发它。留存策略目前是**只写在代码里，从未执行**。

### 6.4 生成式 AI 服务合规

- **算法备案** + **大模型服务备案**（若具备舆论属性或社会动员能力）
- **实名制**：`register_user` 当前只校验用户名 ≥2 字符、密码 ≥6 字符，需加手机号验证
- **AI 生成内容标识**：界面常驻标识 + 导出内容含声明
- **未成年人保护**：年龄门槛，本产品性质不适合未成年人
- **语料合法性说明**

### 6.5 数据主体权利

| 权利 | 现状 | 目标 |
|---|---|---|
| 同意留痕 | 根目录一个 `.privacy_consent` 文件，**仅 CLI 生效**，Web 完全绕过 | 每用户、每协议版本、带时间戳与 IP 入库 |
| 数据导出 | `core/exe_lifecycle.create_exe_export` **是死代码**；`core/exporters/conversation.py` 能跑但读的是空数据（D-02） | 账户级导出，含全部个人信息，且数据得是真的 |
| 数据删除 | `routes.py:369` 裸 `shutil.rmtree`。**当前恰好完整**（所有数据都在 `exes/<slug>/` 下），但缓存未清导致 D-01；且 M1 数据外迁后这个删除会立刻变得不完整 | 级联删除 PG + 对象存储 + 向量库 + 缓存 + 备份，并有自动化验证脚本 |
| 账户注销 | 无 | 完整流程 + 冷静期 + 删除回执 |

**特别提醒**：删除逻辑的完整性目前依赖"所有数据都在一个目录下"这个巧合。M1 把数据拆到 Postgres、对象存储、pgvector 之后，如果不同步改造删除路径，**合规能力会因为架构升级而倒退**。这必须写进 M1 的验收标准。

3. 数据删除必须是**级联且可验证**的，验证脚本进 CI

## 8. 详细需求

编号规则：`FR` 功能需求，`NFR` 非功能需求，`D` 引用第 2 节缺陷。每条给出可判定的验收标准。

### 8.1 M-1 接线与止血（第 1–2 周）

这个里程碑在 v1.0 里不存在。它成本最低、收益最高，且是后续一切的前提。

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-000 | 修复 D-01：引擎缓存键加租户维度，删除/创建/回滚/更新四处全部触发失效 | 新增回归测试：A 创建→对话→删除→B 创建同名→B 的回复不含 A 的人格内容 |
| FR-001 | 修复 D-02：流式路径落库 | 流式对话结束后 `conversation.jsonl` 有记录；客户端中断时已生成部分也落库 |
| FR-002 | 修复 D-03：slug 加租户命名空间 | 两个用户可创建同名镜像；创建接口不再泄漏他人 slug 存在性 |
| FR-003 | 修复 D-04：导入不再阻塞事件循环 | 导入进行中，其他用户的 `/chat` P95 不受影响（压测验证） |
| FR-004 | 修复 D-05：流式路径取真实 usage | 流式与非流式的计量口径一致，偏差 < 5% |
| FR-005 | 接线关系阶段：`STAGE_INSTRUCTIONS` 注入 system prompt | 切换阶段后回复语气可观测变化，评测集可区分四个阶段 |
| FR-006 | 会话摘要与人格更新从 CLI 提取为共用服务并接入 Web | Web 对话满 `ARCHIVE_THRESHOLD` 轮后生成摘要，`sessions/` 非空，下一轮 prompt 含记忆层 |

**项目自己记录的脆弱性**：`CLAUDE.md` 写着「CSS class 名称不可重命名（app.js 动态引用 94 个 class）」。这说明 JS 与 CSS 之间存在大量**隐式契约**，且团队已经意识到了——但契约只写在文档里，没有固化成测试。任何前端改动都依赖人工回归。

**建议**：不急于引入构建工具链（会打断现有交付节奏）。先做两件事——ESLint 接进 CI；关键路径 E2E（登录 → 创建 → 导入 → 对话 → 删除五条主链路）。把隐式契约变成会失败的测试，比写更多文档有效。

## 14. 迁移策略

每条路径都必须留有回滚点。

### 14.1 slug 命名空间化（M-1，最先做）

存量数据少（当前 6 个镜像），是**最好的下手时机**。越往后拖，迁移成本越高。

1. 目录结构改为 `exes/<account_id>/<slug>`，或数据库主键 + 目录用 UUID
2. 存量按 `meta.json` 的 `owner_user_id` 归位；无 owner 的（如 `test`、`1`）人工确认后归档或删除
3. 唯一约束改为 `(account_id, slug)`
4. 回滚点：迁移前完整快照 `exes/`

### 14.2 SQLite → PostgreSQL

1. Postgres 建表（Alembic），**双写**
2. 后台回填历史，逐表校验行数与抽样一致性
3. **灰度切读**：按用户 ID 哈希分批
4. 观察一个完整周期后停双写，SQLite 转只读归档
5. 回滚点：切读阶段任一批次异常立即切回，双写期间 SQLite 始终完整

### 14.3 ChromaDB → pgvector

1. 按镜像**重建**向量而非迁移向量 —— 更可靠，且可同时应用 3 轮/重叠 1 的新分块参数与修复后的 collection 命名（D-13）
2. 每个镜像跑 evals 指标对比，劣化超 2 个百分点则挂起人工排查
3. **双读比对期**：同时查两边，记录差异但只返回 Chroma 结果
4. 差异率达标后切读，Chroma 数据保留 30 天
5. 回滚点：切读后发现问题改回读 Chroma

### 14.4 本地文件 → 对象存储

1. 新写入双写
2. 后台迁移存量，按 checksum 校验
3. 读路径优先对象存储、回落本地
4. 校验通过后停本地写入，保留本地副本 30 天
5. **同步改造删除路径**，并重跑删除完整性验证脚本（NFR-034）

### 14.5 进程内状态 → Redis

接口不变可直接替换，但切换瞬间限流窗口与用量计数会重置，选低峰期发布并公告。引擎缓存失效需额外加跨副本广播。

## 15. 明确不做

| 不做 | 理由 |
|---|---|
| 心理诊断、治疗、咨询 | 无资质，属医疗行为。危机干预限于识别、中断、转介 |
| 真人音色克隆（首期） | 《民法典》第 1023 条声音权益，未经本人授权侵权风险明确 |
| 用用户语料训练 / 微调模型 | 合法性基础不足，与"不做跨用户聚合"的承诺冲突 |
| 镜像分享、公开展示、社交传播 | 第三方个人信息扩散风险不可控 |
| 承诺"复活""永生"等表述 | 伦理与广告合规风险，且加剧用户沉溺 |
| 未成年人服务 | 产品性质不适合 |
| 首期做团队 / 企业组织架构 | C 端 SaaS 优先，但数据模型预留 `account` 抽象 |
| 首期做私有化部署 | 与 SaaS 主线冲突，放 P2 |
| 海外合规与数据分区 | 放 P2 |
| 用调高 temperature 来制造"不完美" | 不完美要在人格层显式建模，随机性不等于人性 |
