## 1. 账号注销时 `safety_events` 的处置

### 决策项

`config.SAFETY_EVENT_DELETION_MODE`，取值 `anonymize`（当前默认）或 `delete`。

### 事实

`safety_events` 表记录危机干预与内容拦截事件，字段包括：

| 字段 | 是否指向自然人 |
|---|---|
| `user_id` | **是** |
| `slug` | 间接（镜像名可能含人名） |
| `excerpt` | **是**（触发文本片段，PII 脱敏后截断 30 字） |
| `input_hash` | 间接（同一文本可比对） |
| `event_type` / `severity` / `created_at` / `detector` | 否 |

### 两种处置

**anonymize（当前默认）**：清空 `user_id`、`slug`、`excerpt`、`input_hash`，
保留类别、严重度、时间。

- 剩余字段不指向任何自然人，可用于聚合分析（危机事件频次趋势、误报率评估、
  干预效果回溯）
- 这些统计对持续改进危机识别有实际价值——召回率调优需要真实分布

**delete**：整行删除，不留痕迹。

- 对「删除权」的解释最彻底，争议最小
- 代价是失去改进识别模型所需的历史分布数据

### 需要法务判断的点

1. 匿名化后的剩余记录，是否仍构成《个人信息保护法》意义上的个人信息？
   若确认已充分匿名化，则不属于该法调整范围，保留不构成违反删除义务。
2. 平台对危机事件是否存在**注意义务下的记录保存必要**？若存在，属于
   「法律法规规定的保存期限」的例外情形，与删除义务如何平衡。
3. 用户注销时若明确要求「彻底删除包括安全记录」，是否应无条件满足？
   （若是，建议在注销流程增加一个选项，而不是全局配置。）

### 切换方式

```bash
SAFETY_EVENT_DELETION_MODE=delete
```

两条路各有测试：`tests/test_account_rights.py::TestDeletionCompleteness` 里的
`test_delete_mode_removes_rows_entirely` 与 `test_anonymize_mode_is_reported_in_receipt`。
删除回执 `receipt["safety_events"]` 会如实报告实际采取的方式。

## 2. 涉政等类目的词表来源

### 现状

`content/moderation_wordlist.zh-CN.json` 里，`vendor_required: true` 的三个类目
（涉政、涉恐、民族宗教）`terms` 为空，**这是预期状态不是遗漏**。

### 理由

这类判定高度依赖语境，静态子串匹配既做不准又容易误伤；且清单需随监管口径
持续更新，属于运营数据而非代码。由代码仓库维护一份必然过时的清单，给的是
虚假安全感。

### 需要决定的

选定内容安全服务商后，用其提供的离线词库填充这三个类目，作为主通道不可用时
的兜底。选型本身影响接入工作量与单次调用成本。

在此之前，这三类内容的拦截**完全依赖第三方主通道**——主通道未接入时，
它们不受任何本地防护。
